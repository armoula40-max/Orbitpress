# معالجة خطأ رفع الوسائط إلى ووردبريس (`rest_upload_sideload_error`)

## العَرَض

عند الضغط على **Publish to WordPress** يظهر:

```
Request failed (500):
{"code":"rest_upload_sideload_error","message":"Sorry, you are not allowed to upload this file type.","data":{"status":500}}
```

بينما ينجح **فحص الاتصال** (Save and test).

## سبب عدم اكتشاف الفحص القديم للمشكلة

الفحص القديم كان ينفذ `GET /wp-json/wp/v2/users/me` فقط، وهو طلب قراءة يثبت أن كلمة مرور التطبيق صحيحة، لكنه لا يختبر:

- صلاحية رفع الملفات (`upload_files`) لدور المستخدم.
- قائمة أنواع الملفات المسموح بها في الموقع.
- تدخل جدار الحماية/WAF (مثل ModSecurity) أو إضافات الأمان التي قد تُفرغ جسم الطلب عند رفع صورة.

أما النشر فينفذ `POST /wp-json/wp/v2/media` بصيغة ثنائية خام، ويمر الملف داخل ووردبريس عبر
`wp_handle_sideload()` ثم `_wp_handle_upload()`، التي ترفض الرفض برسالة "Sorry, you are not
allowed to upload this file type." عندما يتعذر مطابقة **امتداد الملف + المحتوى الفعلي** مع
قائمة MIME المسموح بها في الموقع.

## الأسباب الشائعة

1. **صور WebP** — أكثر سبب شائع. ووردبريس لم يضف WebP إلى الأنواع المسموحة قبل الإصدار 5.8،
   وفي تنصيبات Multisite غالباً لا تكون `webp` ضمن قائمة Network Admin → Settings →
   Upload Settings → "Upload file types"، كما تزيلها بعض إضافات الأمان.
2. **دور المستخدم لا يملك `upload_files`** — يلزم دور Administrator أو Editor أو Author
   (حساب Subscriber غير كافٍ).
3. **جدار حماية/إضافة أمان** يُسقط جسم الملف الثنائي عند الإرسال إلى `wp-json/wp/v2/media`.
4. مزوّد صور يعيد صيغة مختلفة عن المعلنة (JPEG في مسار مُعلّن PNG، أو WebP في مسار JPEG).

## ما الذي عالجه التطبيق

1. **تحويل WebP إلى JPEG تلقائًيا عند حدود ووردبريس** قبل الإرسال (JPEG مقبول في كل تنصيبات
   ووردبريس بما فيها الإصدارات القديمة وMultisite)، مع تسطيح الشفافية على خلفية بيضاء وحد
   أقصى للضغط على الذاكرة (4096 بكسل لأطول ضلع، جودة 90). نسبة 2:3 لصور Pinterest تبقى
   محفوظة تماماً لأن الأبعاد لا تتغير.
2. **إعادة محاولة تلقائية مرة واحدة بصيغة JPEG قياسية** عند ورود
   `rest_upload_sideload_error` أو `rest_upload_image_type_not_supported` لأي صورة (مثل PNG
   يرفضها الخادم).
3. **رسالة خطأ إرشادية** عند استمرار الفشل بعد إعادة المحاولة، تميز بين:
   - مشكلة صلاحية الدور (`rest_cannot_create`) → التوجيه لاستخدام حساب يملك `upload_files`.
   - رفض نوع الملف/إفراغ الجسم → التوجيه للتأكد من رفع JPEG داخل wp-admin → Media ومراجعة
     جدار الحماية لدى الاستضافة.
4. **فحص الاتصال أصبح يرفع صورة JPEG اختبارية صغيرة ثم يحذفها فوراً** عبر
   `POST /wp/v2/media` ثم `DELETE /wp/v2/media/{id}?force=true`، حتى يفشل الفحص في صفحة
   الإعدادات بدل أن يفشل النشر لاحقاً.
5. **تطبيع مخرجات مزوّدي الصور وفق البايتات الفعلية** (`PublishingContracts.detectImageMimeType`):
   إذا أعاد مزوّد متوافق مع OpenAI صورة JPEG أو WebP بدلاً من PNG المعلن، تُوسَم الصورة
   بصيغتها الحقيقية، والبيانات غير المعروفة تُحوَّل إلى JPEG عبر Android Bitmap.

## إجراءات مطلوبة على الموقع فقط إذا استمر الخطأ بعد تحديث التطبيق

- التأكد من قدرة الحساب على رفع JPEG من **wp-admin → Media → Add New**.
- في Multisite: إضافة `webp` إلى القائمة Network Admin → Settings → Upload file types
  (لم يعد ضرورياً بعد تحديث التطبيق لأنه يحوّل WebP إلى JPEG، لكنه يحل رفع WebP يدوياً).
- مراجعة إضافات الأمان وقواعد ModSecurity لدى الاستضافة للسماح برفع الملفات إلى
  `/wp-json/wp/v2/media`.
- التأكد أن مجلد `wp-content/uploads` قابل للكتابة.
- التأكد من استخدام حساب بدور Administrator/Editor/Author لكلمة مرور التطبيق.

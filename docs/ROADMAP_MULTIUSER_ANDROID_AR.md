# خارطة الطريق: واجهة متجاوبة، تطبيق أندرويد بحسابات Google، ولوحة مدير

الوثيقة تترجم الفكرة إلى تصميم عملي قابل للتنفيذ على مراحل، مع الحفاظ على ميزة OrbitPress الحالية: خادم واحد على الـVPS يشغّل كل المنطق (توليد، WordPress، Pinterest، Playwright) والواجهة مجرد واجهة ويب. هذا يجعل التطبيق خفيفًا ويجعل التحديثات تصل للمستخدمين دون إعادة توزيع APK.

---

## المرحلة 1 — تحسين الواجهة وتجربة المستخدم (منفّذة)

واجهة ويب واحدة تعمل على الهاتف والحاسوب اللوحي والحاسوب:

- نقاط توقف (breakpoints): هاتف صغير حتى 480px، هاتف حتى 619px، لوحي من 620px، حاسوب من 980px، شاشات عريضة من 1280px.
- على الحاسوب تتحول شاشات الاستوديو والإعدادات والمحلّلات إلى شبكة من 12 عمودًا: البطاقات تتوزع في عمودين، بينما المحرّرات الطويلة (البرومبتات، تحرير المقال، معاينة المقال، استوديو الدبوس) تبقى بعرض كامل أو بعمود قراءة مريح (900px).
- إصلاحات هواتف: حقول الإدخال بحجم خط 16px لمنع تكبير iOS التلقائي عند التركيز، أهداف لمس لا تقل عن 44px للأزرار الأساسية، تباعد آمن للحواف (notch)، دعم `100dvh`، منع التمرير الأفقي.
- سهولة الوصول: حلقات تركيز مرئية للوحة المفاتيح، احترام `prefers-reduced-motion`، شريط علوي ولوحة قائمة متجاوبان، لوحة الدبوس تكبر على الحاسوب (حتى 400px).
- وسوم PWA أساسية (theme-color، apple-web-app) تمهيدًا للتثبيت على الشاشة الرئيسية لاحقًا.

## المرحلة 2 — المستخدمون وتسجيل الدخول بحساب Google

### 2.1 نموذج الهوية

- الدخول حصريًا عبر **Google Sign-In**؛ لا كلمات مرور محلية للمستخدمين النهائيين.
- العميل يحصل على **Google ID Token** (JWT موقّع من Google) ويرسله إلى الخادم:
  - على الويب: Google Identity Services (`accounts.google.com/gsi/client`).
  - على أندرويد: Credential Manager + `GetGoogleIdOption` (المسار الرسمي الحديث بدل GoogleSignInputClient القديم).
- الخادم يتحقق من التوقيع عبر مفاتيح Google العامة (JWKS من `https://www.googleapis.com/oauth2/v3/certs` مع كاش قصير العمر)، ومن الحقول:
  - `iss` ∈ {`https://accounts.google.com`, `accounts.google.com`}
  - `aud` = معرّف عميل الويب أو أحد معرّفات عميل أندرويد المعتمدة (مخزّن في متغيرات البيئة)
  - `exp` ساري، و`email_verified=true`
- بعد التحقق يصدر الخادم **جلسة خاصة به**: JWT قصير/متوسط العمر داخل كوكي `HttpOnly; Secure; SameSite=Lax` مع ملف تحديث (refresh) على الخادم. Google لا تُستدعى في كل طلب.

### 2.2 حالات المستخدم والأدوار

يُسجَّل كل دخول ناجح لأول مرة في `users.json` بحالة:

| الحالة | المعنى |
|---|---|
| `pending` | سجّل الدخول لكنه بانتظار موافقة المدير — لا وصول للواجهة |
| `active` | موافق عليه — مساحته الخاصة متاحة |
| `blocked` | محظور — يُرفض تسجيل الدخول فورًا مع رسالة واضحة |

الأدوار:

| الدور | الصلاحيات |
|---|---|
| `owner` | مالك الخادم (يُبذَر من `ORBITPRESS_OWNER_EMAIL`) — صلاحيات كاملة |
| `admin` | يقبل/يحظر، يرى الحالة العامة والسجلات والحصص |
| `user` | يرى بياناته هو فقط |

أدوات تحكم بيئية إضافية: `ORBITPRESS_ALLOWED_EMAIL_DOMAINS=domaine.com` (قيد اختياري على النطاقات)، `ORBITPRESS_INVITE_ONLY=1` (كود دعوة مع التسجيل الأول).

### 2.3 العزل — كل مستخدم مساحته الخاصة

البنية الحالية للبيانات مشتركة:

```
data/workspace.json  data/settings.json  data/images/  data/sessions/
```

تصبح لكل مستخدم:

```
data/
  users/<google-sub>/
    workspace.json          # المسودات، الطابور، السجلات، التصنيفات
    settings.json           # Article API / Image API / WordPress / Pinterest / البرومبتات (مشفّرة الأسرار)
    images/                 # صور ذلك المستخدم فقط
    browser/<platform>/     # ملفات Playwright المنفصلة (كوكيز Pinterest/Facebook لكل مستخدم)
  users.json                # google-sub, email, name, role, status, quotas, timestamps
  audit.logl                 # سجل أحداث أمني عام (دخول، موافقة، حظر، رفض)
```

قواعد العزل:

- كل عملية خدمة تأخذ `req.user` وتُقيَّد مساراتها تحت مجلد المستخدم؛ لا يوجد أي مسار يقبل معرّف مستخدم من العميل.
- مفاتيح API وكلمات وردبريس تبقى مشفّرة، ويُشتق مفتاح تغليف لكل مستخدم يُغلَّف بالمفتاح الرئيسي للخادم — حتى المدير لا يستطيع رؤية الأسرار (تظهر له علامة «مضبوط» فقط).
- ملفات Playwright منفصلة تمامًا: جلسة Pinterest للمستخدم «أ» لا يمكن أن يستعملها المستخدم «ب» (يتجنب أيضًا حظر Pinterest لتشارك الجلسات).
- المهلة والحصص لكل مستخدم (انظر 2.5).

ترحيل سلس: عند أول إقلاع بعد التحديث، إن وُجدت بيانات قديمة مسطّحة تُنقَل إلى مجلد مالك الخادم (`ORBITPRESS_OWNER_EMAIL`) تلقائيًا مع نسخة احتياطية قبل الترحيل.

### 2.4 تغييرات الخادم (نقاط النهاية)

| النقطة | الوصف |
|---|---|
| `POST /api/auth/google` | استلام ID token، التحقق، إنشاء/جلب المستخدم، إصدار جلسة |
| `POST /api/auth/logout` | إبطال جلسة المتصفح |
| `GET /api/me` | الهوية، الدور، الحالة، الحصص — الواجهة تضبط نفسها عليها |
| `GET /` وكل `/api/*` | بوابة موحّدة: بلا جلسة = صفحة الدخول؛ `pending/blocked` = صفحة حالة؛ `active` = التطبيق |
| `GET/POST /api/admin/users` | إدارة المستخدمين (admin/owner فقط) |
| `POST /api/admin/users/:id/status` | قبول/حظر |
| `GET /api/admin/overview` | أعداد، نشاط، سعة التخزين، آخر ظهور |

التوافق الخلفي: إن لم تُضبط `GOOGLE_CLIENT_IDS` يبقى الخادم يعمل بنمط المالك الواحد الحالي (`ORBITPRESS_TOKEN`) دون أي تغيير على النشر القائم حاليًا.

### 2.5 حصص وحماية الموارد

Playwright وتوليد الصور باهظان، لذلك لكل مستخدم:

- حصة يومية: مقالات، صور، دبابيس، دقائق متصفح (قيم افتراضية يغيّرها المدير لكل مستخدم).
- حد متزامن للمهام الثقيلة عبر طابور لكل مستخدم (لا يمكن لمستخدم واحد أن يستهلك المتصفح كله).
- `express-rate-limit` على نقاط الدخول والتوليد، ورأس زمني موحّد للمهام.
- سعة تخزين الصور لكل مستخدم مع تنظيف صور غير مرجعية.

## المرحلة 3 — تطبيق المدير

التوصية: **لوحة مدير داخل نفس الخادم** (`/admin` داخل الواجهة، مخفية تمامًا ما لم يكن الدور admin/owner) + **نكهة بناء (flavor) مدير في مشروع أندرويد**. هذا يعطي «تطبيق مدير» منفصلًا على الهاتف (معرّف تطبيق مختلف وأيقونة مختلفة) مع إعادة استخدام كامل الكود بدل صيانة مشروعين.

### 3.1 شاشات لوحة المدير

1. **طلبات الانضمام**: قائمة `pending` مع البريد والاسم ووقت أول دخول، زرّا «قبول»/«حظر» وأزرار «قبول بنطاق البريد كله».
2. **المستخدمون**: بحث، تصفية حسب الحالة، تعديل الحصص، حظر فوري، إنهاء جلساته.
3. **النظرة العامة**: مستخدمون نشطون الآن، مقالات/دبابيس آخر 24 ساعة، أخطاء المزودات، مساحة التخزين، حالة قائمة انتظار المهام.
4. **سجل التدقيق**: دخول/خروج، قرارات الموافقة/الحظر، تغيير الحصص، أخطاء مكررة — للقراءة فقط مع تصدير.
5. **الحالة الصحية للنظام**: ذاكرة/قرص الحاوية، نسخة البناء، صلاحية اتصال المزودات العامة، إمكانية إعادة تشغيل مهام المتصفح.

### 3.2 حدود الخصوصية (مهمة)

- المدير يرى: الأسماء، الأرقام، الحالات، السجلات العامة، أنواع المزودات المضبوطة.
- المدير لا يرى: مفاتيح API، كلمات وردبريس، كوكيز Pinterest، محتوى المسودات (خاصة). أي «دخول كالمستخدم» للدعم يكون خلف تأكيد صريح ويُسجَّل في سجل التدقيق مع شعار ظاهر داخل الجلسة.
- كل إجراء مدير يُكتب في `audit.logl` (مَن، متى، ماذا).

### 3.3 إشعارات المدير (فكرة إضافية موصى بها)

- عبر FCM على جهاز المدير: طلب انضمام جديد، فشل متكرر في التوليد، امتلاء القرص.
- نفس قناة FCM تُستعمَل لإشعار المستخدم العادي: «مقالك جاهز»/«اكتمل النشر على Pinterest».

## تطبيق أندرويد (المرحلة 2 تقنيًا، يُسلَّم بعدها)

مشروع `app/` الحالي (Kotlin، WebView) يُعاد توجيهه ليصبح غلافًا رفيعًا:

1. شاشة أولى لإدخال عنوان الخادم (مثل `https://orbit.example.com`) يُتحقق منه ويُحفَظ.
2. زر **تسجيل الدخول عبر Google** أصلي (Credential Manager) → إرسال ID token إلى الخادم → استلام كوكي الجلسة → حقنه في WebView (CookieManager، آمن، SameSite) → فتح الواجهة.
3. الواجهة نفسها تُعرَض داخل WebView: كل التحسينات الجديدة (PWA، التجاوب، رفع الملفات، الإشعارات) تعمل دون تعديل؛ أي تحديث ميزات يصل فورًا من الخادم.
4. ملفات تعريف بناء (product flavors):
   - `user` → `com.orbitpress.app` (أيقونة المستخدم، يفتح `/`).
   - `admin` → `com.orbitpress.admin` (أيقونة مختلفة، يفتح `/admin` ويرفض الحسابات غير المديرة).
5. روابط `Digital Asset Links` و`assetlinks.json` إن اخترنا لاحقًا تحويل الغلاف إلى TWA عبر Bubblewrap (تجربة أقرب للتطبيق الأصلي ومتجر Play بنفس الكود تقريبًا).
6. إضافات: FCM للإشعارات، زر مشاركة النظام، فتح الروابط الخارجية في Chrome Custom Tabs، كشف انقطاع الخادم بصفحة خطأ عربية أنيقة.

لماذا WebView/TWA وليس تطبيق React Native/Flutter من الصفر؟ المنطق كله على الخادم أصلًا، والمطلوب هو هوية Google وإشعارات وتجربة ويب كاملة؛ الغلاف الرفيع يقلّص الصيانة ويضمن تطابق الويب والهاتف دائمًا.

## ترتيب التنفيذ المقترح (مراحل تسليم)

| المرحلة | المخرجات | اختبار القبول |
|---|---|---|
| **م1: الواجهة** (تمّت) | CSS متجاوب + PWA أساسيات | الواجهة متماسكة على 390px و768px و1440px بلا تمرير أفقي |
| **م2: الهوية والعزل** | تحقق Google، جلسات، users.json، مجلدات المستخدمين، ترحيل بيانات المالك | مستخدمان لا يرى أحدهما مسودات/جلسات/صور الآخر؛ blocked مرفوض؛ المالك القديم يعمل دون إعداد |
| **م3: بوابة الموافقة** | حالات pending/active/blocked + صفحات حالة عربية | المستخدم الجديد ينتظر حتى يقبله المدير |
| **م4: لوحة المدير** | مستخدمون، حصص، نظرة عامة، سجل تدقيق | المدير يقبل/يحظر/يعدّل الحصة وتنعكس فورًا |
| **م5: تطبيقا أندرويد** | flavor المستخدم + flavor المدير، Google أصلي، FCM | دخول Google من APK ينتهي بكوكي جلسة صالحة وإشعار اكتمال المهمة يصل |
| **م6: تصليب** | حصص، rate limit، تنظيف تخزين، نسخ احتياطي | إساءة الاستخدام محدودة دون تدخل، والاستعادة من نسخة احتياطية موثّقة |

## ملاحظات أمان ختامية

- لا يُعتمد على التحقق من الدور في الواجهة فقط — كل نقطة `/api/admin/*` محمية على الخادم.
- ID token للهوية فقط؛ الأسرار تُغلَّف بمفتاح الخادم، لا بمفتاح Google.
- كل الكوكيز `Secure; HttpOnly`، والخادم خلف HTTPS (Nginx على الـVPS كما في النشر الحالي).
- الجلسة تُربط بمعرّف جهاز اختياريًا، و«تسجيل الخروج من كل الأجهزة» يُبطِل رموز التحديث.
- وضع الصيانة: علامة بيئية توقف المهام الجديدة مع صفحة صيانة عربية أنيقة.
